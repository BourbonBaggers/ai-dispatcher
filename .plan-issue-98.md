# Issue #98: Post-ship audit — backoff, an attempt cap, and a terminal state

## Goal
`sweepPendingAudits` retries every `unavailable` audit on every scan, forever, and a
retry after a judge verdict spends another judge call. Give each audit a durable attempt
counter and next-attempt time, back off (5 min, 30 min, 2 h, then daily), stop after 6
attempts or a permanent failure with a terminal `audit: { status: "unavailable", reason }`,
read every piece of evidence before the judge runs, and fall back to the PR files API when
GitHub refuses a diff as too large. The audit stays advisory: nothing here may hold, page,
or spend recovery budget.

## Facts established (code at 7da8b53, production read-only)
- Production `ai-dispatcher.service` polls `BourbonBaggers/internal-tools` at
  `--interval 60`. Its state has three `pending` audits: #728 (PR #746), #737 (PR #760),
  #772 (PR #776); #771 failed creation twice and then went clean on a third judge verdict.
- #737: `gh pr diff 760` exits 1, stdout empty, stderr
  `could not find pull request diff: HTTP 406: Sorry, the diff exceeded the maximum number
  of files (300). ...` and `PullRequest.diff too_large`. Deterministic.
- `gh api --paginate repos/<slug>/pulls/760/files?per_page=100` succeeds: 305 files
  (302 removed, 2 modified, 1 added), ~18 KB of names but ~1.1 MB of patches, so the
  fallback evidence must be budgeted against the judge's 60 000-char diff slice.
- #728/#771/#772 creation failures: `internal-tools` has `dispatch:ready` but neither
  `audit-followup` nor `audit:depth-1`; no audit follow-up was ever created there. gh
  resolves `--label` names to IDs before the create mutation and fails the whole command
  with `could not add label: '<name>' not found`, creating nothing. The ai-dispatcher repo
  has both labels (created by hand); nothing in the dispatcher provisions them.
- `gh issue list --label audit-followup` on a repo without that label exits 0 with `[]`.
- The existing-follow-up search runs AFTER the judge today, so its failure wastes a judge
  call. `auditShippedIssue` exceptions are logged and retried on the next scan, uncounted.
- `GithubClient.createIssue` returns `number | null`, discarding gh's error text, and
  `prDiff` returns `string | null`, so neither failure can be classified today.

## [DONE] Milestone 1: Pure retry policy and durable audit attempt state
- New pure `src/acceptance-retry.ts`: `AUDIT_MAX_ATTEMPTS = 6`, `AUDIT_RETRY_DELAYS_MS`
  (5 min, 30 min, 2 h, 24 h; the last repeats), `auditRetryDelayMs(attempts)`,
  `auditDue(audit, nowMs)`, `auditAfterFailure(previous, failure, nowMs)` -> pending with
  backoff, or terminal `unavailable` at the cap / on a permanent or repeated failure, and
  `creationFailureSignature(error)` (normalized gh error; transient-looking errors such as
  rate limits, 5xx, timeouts, and network failures never count as "the same way").
- `src/state.ts`: `audit.status` gains `unavailable`; optional `attempts`,
  `nextAttemptAt`, `reason`, `failureSignature`. Legacy `{status:"pending", at}` records
  need no migration: no attempts and no next time mean "due now, nothing spent".
- Tests: `test/acceptance-retry.test.ts` (schedule, cap, permanent, repeat signature,
  transient exclusion, legacy record) and a state round-trip case.
