# Issue #97: Scan loop — stop sleeping a full poll interval while work is in flight

## Goal
`runLoop` sleeps `pollIntervalSeconds` (default 900 s) after every scan, so a parked
run's CI recheck and the next issue's pickup each wait up to a full interval. Choose the
sleep from what the scan did: a short active interval while work is moving or parked, the
idle interval when there is nothing to do, and a bounded backoff after errors. Lower the
idle default to 60 s, and keep an idle scan cheap enough to run every minute: list open
issues and nothing more — in particular, no Claude/Codex usage-endpoint reads.

## Facts established (code at d3821cc)
- `runScanOnce` calls `pickupCapacity` unconditionally after finalization/audits, so every
  scan — idle ones included — reads the Claude OAuth usage endpoint and spawns
  `codex app-server`. Capacity is consumed only by resumable-run suppression/handoff,
  fresh-issue routing (`assignmentForIssue`, issue-text refinement), and escalation.
- `selectEligibleIssue` already rejects issues before routing (author, dispatch request,
  hold labels, existing claim); capacity matters only for issues that survive that.
- `deps.readCapacity` falls back to the live, uncached `readLiveCapacity`, so tests that
  do not inject a reader hit the real endpoints with this host's credentials.
- Escalation re-reads capacity per rung (test asserts `capacityReads > 1` on a frozen
  clock); a cache must therefore live in the production reader, not inside the dispatcher.
- The blocked-queue audit runs on every scan that finds no target and invokes a model CLI
  per blocked candidate (up to 3). At a 60 s idle interval that is 15x the model calls of
  the old 900 s default.
- A parked run always short-circuits the scan at the parked branch, so "left a run parked"
  is covered by classifying each scan return explicitly.
- The dashboard predicts the next scan from the last `scan complete` line plus a fixed
  interval (fallback 900); `.env.example` must list exactly the env read by `config.ts`.

## Milestone 1: Choose the sleep from each scan's outcome
- New pure `src/scan-cadence.ts`: `ScanOutcome = active | idle | error`, default active
  (20 s) and idle (60 s) intervals, `nextScanDelaySeconds(outcome, consecutiveErrors,
  cadence)`: active -> active interval (never longer than idle); idle -> idle interval;
  error -> active x 2^(n-1), capped at the idle interval.
- `src/config.ts`: `activeIntervalSeconds` from `--active-interval` /
  `DISPATCHER_ACTIVE_INTERVAL_SECONDS`; idle default 900 -> 60; usage text.
  `.env.example` documents both.
- `src/dispatcher.ts`: `ScanResult.outcome` is required. Started, resumed, handed off,
  escalated, finalized, rechecked (parked/ready/held), shipped, needs-input hold applied,
  or stale `blocked` removed -> `active`; nothing to do -> `idle`; issue listing failed or
  needs-input hold could not be applied -> `error`.
- `src/main.ts` `runLoop`: count consecutive errors (thrown scans and `error` outcomes),
  sleep `nextScanDelaySeconds`, log `outcome` and `nextScanSeconds`. `--once`/`--dry-run`
  still run exactly one scan and never sleep. Injectable scan/sleep hooks for tests.
- Tests: `test/scan-cadence.test.ts`, `test/main-loop.test.ts`, `test/config.test.ts`,
  outcome assertions in `test/dispatcher.test.ts`.
- Commit as `milestone(1): ...`.

## Milestone 2: Read live capacity only when a run is about to be assigned
- `src/selection.ts`: export the routing-independent checks (`preRoutingIneligibility`,
  `hasRoutableIssue`) and use them inside `selectEligibleIssue` (reasons unchanged).
- `src/dispatcher.ts`: load capacity lazily, at most once per scan — only when a resumable
  run must be judged, or when a listed issue survives the pre-routing checks.
- `DispatcherDeps.readCapacity` no longer defaults to a live read; `buildDeps` wires
  `readLiveCapacity` explicitly, so production is unchanged and tests are hermetic.
- Tests: idle scans (empty queue, only held/claimed/unqueued issues) make zero capacity
  reads; routable issues and resumable runs still read once.

## Milestone 3: Cache live capacity reads for 60 seconds

  TTL, concurrent callers share the in-flight read, a clock moving backwards re-reads.
- `src/main.ts` `buildDeps`: wrap `readLiveCapacity` in the cache.
- Tests in `test/capacity-adapters.test.ts` and `test/main-loop.test.ts`.
