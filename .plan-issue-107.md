# Issue #107: Remove a run's checkout after it ships, and prune stale checkouts

## Goal
#102 asked for checkout cleanup. Its PR (#106) merged only a stray `.dispatcher-deps-key`,
so none of the behavior exists and the audit follow-up is correct. Implement it: remove
a shipped run's checkout, keep failed/abandoned ones for a retention window (never deleting
unpushed commits), prune old unrecorded directories, delete gently one directory at a
time, and guard launches against a nearly full disk.

## Facts established (code at 4ff3e43, production read-only)
- `scripts/dispatch-agent.sh` makes each checkout with `git clone <mirror>` into
  `<DISPATCHER_WORKTREE_DIR>/<branch>`. These are clones, not `git worktree`s. The branch
  name always matches `^issue-[0-9]+(-[a-z0-9-]+)?$`, and `RunRecord.checkoutPath` is
  `join(worktreeDir, branch)`.
- Nothing removes a checkout today. `pruneOldRuns` keeps 100 records, so checkouts of
  pruned runs become directories with no run record.
- On this host both services (`ai-dispatcher.service` for internal-tools,
  `ai-dispatcher-self.service` for this repo) run from one deployment checkout and share
  a 195 GB root disk, currently 94% full (13 GB free). Every one of the 164 + 39 entries
  under the two worktree dirs matches the branch-name pattern, and each `.git` is a
  directory.
- 25 sampled production checkouts: 0 had unpushed commits; 5 had leftover uncommitted
  edits; `git status` took about 5 s each under the current I/O load. Protecting dirty
  trees would keep a fifth of all checkouts forever, and the launcher already discards a
  terminal run's uncommitted leftovers (`reset --hard` + `clean`) on a fresh start. Only
  unpushed commits are protected, as #102 specifies, using `rev-list` (no working-tree
  scan). The launcher's own `plan: checkpoint` commits are not agent work.
- A shipped run whose `finalizationPending` is still set can still be replayed and
  relaunched in resume mode, which dies if the checkout is missing. Removal must wait
  until finalization has cleared.
- Self-ship health is just "unit active with an unchanged PID after 14 s", so a startup
  sweep cannot trip rollback unless it crashes the process.

## Design
- Pure policy (`src/checkout-retention.ts`): per directory, using every run record that
  points at it.
  - **Keep:** any claiming or unknown status, or any record whose finalization is pending.
  - **Remove now:** every record `shipped`.
  - **Retain, then verify:** a `failed`/`abandoned` record (or a mix including one) is kept
    until retention expires, measured from the later of the run's end and the directory's
    last activity. After that it is removed if it has no unpushed commits.
  - **Orphans:** a directory with no record is removed once unmodified for the retention
    window and free of unpushed commits.
  - **Disk guard:** the guard trips below the smaller of 10 GB and 10% of the filesystem.
    Either floor at 0 disables it.
- IO (`src/checkout-cleanup.ts`), all fail-closed:
  - Only directories directly under the worktree dir whose names match the launcher's
    branch pattern are touched. Symlinks and the dispatcher's own paths are never touched.
  - A `/proc` scan (cwd/root/exe/fds/maps) skips any directory a process uses. When
    `/proc` is unavailable, the check is unknown and nothing is removed.
  - Deletion runs under `ionice -c2 -n7 nice -n 19`, one directory at a time. A linked
    worktree is removed with `git worktree remove --force`, falling back to `rm -rf`, and
    `git worktree prune` then runs on the mirror. Branch refs are never deleted.
  - Each removal logs one line, and each sweep logs one summary with the bytes freed
    (the statfs delta).
- Scheduling (`src/dispatcher.ts`):
  - Every scan, after pending finalization, removes settled shipped checkouts (cheap).
  - The full sweep runs on startup and then daily.
  - Before a fresh launch, and before a resume the scan starts on its own, a low disk
    triggers cleanup (at most every 15 min). If space is still low, the launch is held:
    no claim, no budget spent, and one warn plus one default-priority notification per
    episode. Ready/parked/held rechecks still run.
  - In-ladder repairs are not gated: they reuse the run's checkout, and holding one
    mid-ladder would strand a delivery.
  - Dry-run never cleans. The cleanup is an optional dependency, so it is inert in
    tests that do not inject it.
