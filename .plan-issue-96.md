# Issue #96: CI wait — a PR whose checks have not registered yet is pending, not failed

## Goal
Stop classifying a just-opened PR as red CI. A PR with no checks registered yet must
keep the launcher waiting until CI resolves, report `CI PASSED` once checks go green,
and fail promptly only on a real failed/cancelled check. Absence past a grace period is
its own "CI did not start" state that parks the run without relaunching an agent or
spending recovery attempts. The same rule applies wherever the dispatcher reads
`gh pr checks`.

## Facts established (gh v2.63.2 installed; latest v2.102.0 source; live reads)
- `gh pr checks <pr> --json name,bucket` on a PR with no registered checks exits 1,
  prints nothing on stdout, and writes `no checks reported on the '<branch>' branch`
  to stderr. `--json` never yields `[]` for that state.
- With `--json`, gh exits 0 whenever it can read the checks, whatever the buckets say.
  Without `--json` it exits 0 (pass), 8 (pending), or 1 — and 1 covers a failed check,
  "no checks reported", and any transport/auth error alike.
- Buckets: `pass` = SUCCESS; `skipping` = SKIPPED/NEUTRAL; `fail` =
  ERROR/FAILURE/TIMED_OUT/ACTION_REQUIRED; `cancel` = CANCELLED; `pending` = the rest.
- Consequences today: the launcher logs `CI FAILED` ~1 s after opening a PR; the resume
  prompt calls a no-checks PR "RED"; and `src/github.ts` `prChecksEvidence` reads the
  no-checks state as `unknown` with `checkCount: null`, so autoship's #60 missing-suite
  grace (`checkCount === 0`) never engages in production. Its first-observed timestamp
  is also never reset once a suite appears.

## [DONE] Milestone 1: Launcher reads structured buckets and waits through absent checks
- Add `scripts/lib/dispatch-ci.sh` (sourced by `dispatch-agent.sh`, testable alone):
  - `ci_checks_verdict`: gh exit code + stderr + `--json` stdout ->
    `pass|fail|pending|absent|unknown`, plus sanitized failing-check lines.
  - `read_pr_ci`: one `gh pr checks --json name,bucket,link` read.
  - `wait_for_pr_ci`: poll every `CI_POLL_SECONDS` up to `CI_WAIT_SECONDS`; absent,
    pending, and unreadable keep polling; absent past `CI_START_GRACE_SECONDS` (120)
    stops as `absent`; only fail/cancel buckets are `fail`.
  - `report_pr_ci`: `CI PASSED` / `CI FAILED` + failing check names /
    `CI DID NOT START` / unresolved-after-deadline events.
- `dispatch-agent.sh`: source the lib, use it for the post-run wait (emitting
  `ci=absent`) and for the resume-prompt red-PR detection.
- Tests with a fake `gh` and a virtual clock: no checks then green, no checks then red
  (names logged), pending then green, no checks past grace, unreadable gh never `fail`,
  check names cannot forge control lines, resume prompt only flags real failures.
- Commit as `milestone(1): ...`.

## Milestone 2: Runner parks `ci=absent` without spending recovery
- `src/sanitize.ts`: accept `ci=absent` on the trusted result line.
- `src/runner.ts`: clean exit + commits + `absent` -> `ci_pending` with a distinct
  "CI did not start" summary, so it never enters the `ci_failed` repair ladder.
- Tests in `test/sanitize.test.ts` and `test/runner.test.ts`.
- Commit as `milestone(2): ...`.

## Milestone 3: Apply the same rule in `src/github.ts` and autoship
- `prChecksEvidence`: `no checks reported` (and an empty list) ->
  `{ state: "pending", checkCount: 0 }`; transport failures stay `unknown`.
- `waitForPrChecks`: keeps polling while absent/pending/unreadable; deadline returns
  `pending`, never `fail`.
- Autoship: clear `ciChecksFirstObservedAt` once a check suite is observed, so a later
  empty read (after a repair push) gets a fresh grace instead of an immediate CI repair.
- Tests in `test/github.test.ts` and `test/autoship.test.ts`.
- Commit as `milestone(3): ...`.
